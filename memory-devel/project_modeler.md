Key decisions locked in the design conversation:
- **Emacs architecture**: small fast Rust kernel + everything-else-in-Janet. Rule: O(pixels/triangles) = Rust primitive; O(events/commands) = Janet. UI is Janet-drawn overlays into the CPU framebuffer (no egui/GPU toolkit) — matches minimalist brief (no toolbars/buttons; pop-menus + hotkeys/hotkey-menus only; viewport = 100% of window).
- **Software rasterizer viewport** (no wgpu/OpenGL/Metal), like ray. Window via `softbuffer + winit` (NOT `pixels` — it presents via wgpu).
- **Sibling crate in the ray cargo workspace**: root stays the `ray` package AND becomes workspace root (add `[workspace] members=["modeler"] default-members=[".","modeler"]`); nothing in `src/` moves; `modeler` depends on `ray` lib (default features = pure-Rust kernel). ray never depends on modeler. Chose this over separate repo (less refactor friction for solo dev) and over the tidier full move-src-into-`ray/` layout.
- **Threading spine (highest risk, proved first at M2)**: Janet VM touched ONLY from the main thread (winit event loop + VM). Render worker (rayon) never calls Janet, posts frames back. REPL socket thread marshals source onto an eval channel drained on the main thread. This reverses my earlier "don't embed Janet" advice — that was for ray's live-render-thread topology; the Emacs single-threaded-command-loop topology dissolves the global-VM issue.
- **Live REPL = first-class** (user requirement): external TCP connection (reuse ray nREPL plumbing / Emacs comint) + `load-script` + in-window minibuffer.
- Native save format = Janet; glTF = import/export (writer is the one new I/O half). Reuses ray: scene/mesh/camera/material/texture types, BVH (for picking), gltf_loader, wireframe (overlay mode), render integrators (settled→trace rung), %-cfunction pattern, ab_glyph text.
- **Render-through-ray = from-day-one requirement (user, 2026-09-03)**: render the current model through the current pane's camera USING ray. Decided **in-process linked library** (NOT separate binary) — ray's render fns already take `(&Scene, &Camera)` and those are the modeler's own live types; it's the render-worker job (rayon worker runs render_progressive/accumulate_pass, posts frames back; blit-to-window OR save-PNG). Forces invariant: live geometry must be `to_scene()`-convertible to a ray Scene at any instant. Separate-binary route comes free via `ray-janet --scene <exported> --out` for batch/final. CAVEAT: ray Camera is perspective-only (pinhole+DOF, no ortho) → render targets the persp pane; ortho-pane render would need an ortho camera added to ray (deferred).
- Milestones A→M9 in the doc, **plus M3.5 = render-through-ray spike** (to_scene + one-shot render()→PNG, pulled early to prove the workspace-sibling round-trip); M9 upgrades it to progressive in-window trace. **near-plane clipping** flagged as the one rasterizer bug surface ray never had (tracer never clips).
- OPEN micro-decision: quad-view focus model (lean = focus-follows-mouse) — deferred to M4.
