The `janet-scripting` branch was then **deleted (local + origin)** since it was fully merged. **NEXT:** (a) decide the `--window` approach (windowing crate + macOS main-thread loop — a real design call for the user) if live preview is wanted; (b) new rendering features.

Rationale for Janet: `ray` is **non-commercial, for creative/art work** (not a product), so the priority is an uninterrupted live-editing loop over raw perf/production-hardening. Janet is **safe by construction** — thread-safe (main-thread-only eval via channel), no global SIGFPE/signal hijack — so a session won't crash or corrupt the scene mid-flow (the thing that kills creative momentum). ECL's advantages were either moot under `ray`'s native-Rust-shader plan (hot-call perf only matters if scripting hot shaders) or already narrowed (DX — SLY is nicer out-of-box, but the hand-built janet-live-mode + docs + janet-lsp coexistence closed most of the gap). ECL's losses (informal Slynk/main-thread thread-safety race, global SIGFPE trap) are systemic robustness liabilities. Perf gap (ECL 0.09µs vs Janet 0.27µs tex) accepted as immaterial for this use. **Next: park the ECL work (ray `ecl-scripting` branch, [[ray-ecl-integration]]); the push-arch Janet ([[ray-janet-poc]]) is the path forward** — bring it into `ray` proper (still on the ray-janet-poc POC repo, not yet merged to ray main).

### Decision-support detail (2026-07-26)

User re-validated [[ray-ecl-poc]] before the call. Ran the ECL POC via SLY on macOS and **called the ECL/SLY user experience "very nice."** Key DX asymmetry: SLY/Slynk gives ECL mature live tooling FOR FREE (completion, arglist, doc lookup, jump-to-def, live edit against the running image), whereas Janet required the hand-built `janet-live-mode.el` + doc-popup elisp (and janet-lsp coexistence). So on live DX, ECL is ahead with zero custom tooling. Perf: ECL leads hot-call math (0.09 µs tex vs Janet 0.27 µs; near-parity Lambert on ARM64 1.1×). Decision still open; DX + perf both currently favor ECL, but note ECL's footguns (SIGFPE trap, informal Slynk/main-thread safety, Nix shell, pull-model architecture not yet migrated to push). ray-ecl-poc is the standalone pull-model POC; the push-arch ECL work lives on ray's `ecl-scripting` branch ([[ray-ecl-integration]]).

**SIGFPE trap — how the shipping branch handles it (checked `origin/ecl-scripting` @2045750, 2026-07-26):** IDENTICAL one-liner `(ext:trap-fpe t nil)` to the POC, now encapsulated in `boot()` in `src/scripting/mod.rs` (cl_boot → trap-disable → NIL, so the "must be first eval" ordering is structural as long as callers use `boot()`, not raw cl_boot) with a good explanatory comment. Only one occurrence on the whole branch. Improves the ordering/forgot-to-call failure mode but does NOT address the substance: still a global process-wide FP-semantics change (silent inf/NaN everywhere, no FP-trap bug detection), no re-assertion/guard if traps get re-enabled, no isolation from host signal handlers, and still the hard embedded-debugger crash if it ever fires. Janet has NONE of this (no global signal handler). Net: real-but-manageable ECL liability, slightly de-risked on ordering. See [[ray-ecl-poc]] SIGFPE section for the full failure-mode writeup.
